# Young Analysts Curriculum and Assessment Specification

## Purpose
Young Analysts develops six observable competencies: computational thinking, data literacy, statistical reasoning, research literacy, AI literacy, and evidence communication. Age bands guide entry; demonstrated evidence guides progression.

## Assessment architecture
Every substantive learning unit should use four layers:
1. **Retrieval check** — short low-stakes questions that test concepts and vocabulary.
2. **Code/data check** — deterministic task with explicit expected behaviour and edge cases.
3. **Applied challenge** — authentic problem requiring an artefact plus explanation.
4. **Reflection/review** — learner explains method, testing, limitation and next improvement.

A single multiple-choice answer must never be the sole evidence of competency.

## Performance rubric
Applied evidence is reviewed on four dimensions, each 0–3:
- **Method & correctness**: 0 absent; 1 partially working; 2 correct core method; 3 correct, robust and appropriately tested.
- **Evidence & testing**: 0 none; 1 one weak check; 2 relevant tests/evidence; 3 boundary/alternative cases plus traceable evidence.
- **Reasoning & communication**: 0 unexplained; 1 describes output; 2 explains method and finding; 3 distinguishes evidence, interpretation and limitation.
- **Responsible practice**: 0 unsafe/inappropriate; 1 prompted correction needed; 2 appropriate data/safety practice; 3 actively minimises data and identifies ethical/quality risk.

Recommended competency threshold: at least 8/12 overall **and no zero in Responsible practice**. This is a programme rule to validate in pilot testing, not a psychometrically established cut score.

## Python for Kids: 10-module evidence map
| Module | Core outcome | Required evidence | Testing emphasis |
|---|---|---|---|
| 01 Welcome to Coding | Sequence exact instructions and correct simple syntax | Three-step algorithm + code card | Syntax and order |
| 02 Talking to Python | Produce clear output and perform calculations | Menu + score/shopping calculator | Expected numeric output |
| 03 Variables & Input | Store and use safe user input | Interactive story/idea generator | Multiple safe inputs; data minimisation |
| 04 Decisions | Implement and test conditional routes | Decision game | Boundary values and every route |
| 05 Loops | Repeat safely and predict termination | Counter/countdown | Iteration count; termination |
| 06 Lists | Store, update and summarise collections | Activity tracker | Index boundaries; totals |
| 07 Functions | Encapsulate reusable transformations | Function toolkit | Multiple inputs; returned values |
| 08 Games | Integrate state, decisions and feedback | Small playable game | Valid/invalid choices; score rules |
| 09 Data | Summarise data and make bounded claims | Mini data story | Calculation, interpretation, limitation |
| 10 Project | Plan, build, test and communicate an original solution | Code + test record + reflection | Acceptance tests and limitations |

## Testing requirements by module
- M01–M03: at least 2 test cases for each applied task.
- M04: test below, at and above a decision boundary where applicable.
- M05: state why the loop terminates; test expected iteration count.
- M06: test list length, first/last valid index and computed summary.
- M07: test a function with at least 3 inputs, including a boundary/simple case.
- M08: test every game route plus invalid input.
- M09: independently verify calculated summaries; explicitly state one limitation.
- M10: define at least 3 acceptance tests before final submission and report expected vs actual results.

## Question-bank quality rules
Each module assessment should contain a balanced mix of:
- concept recognition;
- predict-the-output;
- debug-the-code;
- choose-the-best-test;
- interpret evidence;
- responsible/safe practice.

Distractors must represent plausible misconceptions, not obviously silly answers. Avoid testing trivia or exact wording from lessons.

## Progression evidence
A learner is ready to progress when evidence is consistent across more than one task. Progress percentage alone is insufficient. Instructor review should consider recent artefacts, test quality, explanation and support needs. No public ranking.

## Pilot validation
Before using scores for certification or consequential progression, review item difficulty, distractor performance, completion time, common error categories and rubric consistency. Revise ambiguous items and tasks with unexpectedly high failure unrelated to the intended competency.
